## Addendum — 2026-08-09 Session 15: in-game header clipped at the top (phone-verses v2.4, sandbox v1.14)

Player-reported with a screenshot: the top of the white in-game header card
was cut off — its rounded top corner and part of the "See passage" pill sat
above the visible area — and the iOS status bar was drawn over the title
("Habakkuk 3:17–19" running into the cellular signal bars).

### Why the diagnosis took three passes

The intermittency ruled out the obvious explanations one at a time, and the
discarded hypotheses are worth recording so they aren't re-tried:

1. **"Content grew taller than the viewport, and `justifyContent: 'center'`
   makes the top overflow unreachable."** Plausible — the header does grow
   during a round (the bonus-moves row only exists once bonus moves are
   earned, the passage text bar grows as lines reveal, the "· 1.5×" marker
   and drill badge add width). **Ruled out** by the user reporting the header
   sitting correctly *with* four revealed lines and the bonus row showing.
   The content fits; it isn't content height that's toggling.
2. **"Safari's toolbar collapse scrolls the page and the game can't scroll
   back."** **Ruled out** by the user seeing it with both the collapsed pill
   *and* the full-width address bar, and by tapping/dismissing the address
   bar not restoring it.

What survived is that the page has scroll room it should never have had, from
two independent sources, and that the scroll is one-way.

### The four contributing causes (all read directly from the code)

1. **No CSS reset exists anywhere in the project.** No stylesheet file is in
   the repo and no entry file imports one — `src/entry-phone-verses.jsx`
   renders straight into `#root`. So `<body>` kept the browser default 8px
   margin, top and bottom, and with the wrapper at `minHeight: 100vh` the
   document was permanently `100vh + 16px` on every load, regardless of
   content.
2. **`100vh` on iOS Safari is the *large* viewport height** — the height the
   page would have with the toolbars hidden. Whenever the toolbar is showing,
   the visible area is shorter, adding a further ~60–90px of scroll room.
   This is the larger of the two sources.
3. **`touchAction: 'none'` on the wrapper** (there so swipes reach the board
   rather than panning the page) means that once the page *is* scrolled, a
   drag can't bring it back. Nothing resets `scrollTop` — there are no
   `scrollTo`, `scrollIntoView`, or `scrollTop` calls anywhere in the file.
4. **`viewport-fit=cover` + `apple-mobile-web-app-status-bar-style:
   black-translucent`** in the HTML tell Safari to run the page under the
   status bar and notch, with no `env(safe-area-inset-top)` padding to
   compensate — a constant ~47–59px overlap. Constant, so it never explained
   the intermittency, but it's why the status bar sat on the title.

The intermittency was simply whether the page happened to be sitting at
scroll 0.

### What shipped

Three changes, identical on both platforms:

- **Body margin zeroed** — `<style>html, body { margin: 0; padding: 0; }</style>`
  added to `phone-verses.html` and `phone-verses-sandbox.html`. Scoped to
  those two pages so no other platform's layout shifts (see the DEFERRED
  entry: the other nine pages still carry the default margin, on purpose).
- **Safe-area top padding** on the game wrapper: `paddingTop: 'calc(env(safe-area-inset-top, 0px) + 8px)'`,
  written as padding **longhands** rather than the shorthand so the value
  can't be clobbered by property order in the inline style object.
- **`minHeight: '100vh'` → `'100dvh'`** — the dynamic viewport unit tracks
  the height actually visible on iOS. (dvh: Safari 15.4+, Chrome 108+,
  Firefox 101+. Without support the declaration is dropped and the purple
  wrapper sizes to its content — cosmetic, not a break.)

### Decision: `justifyContent: 'center'` left alone

Top-anchoring the wrapper would make top clipping structurally impossible,
but it also moves the game to the top of the screen on every device where it
currently fits — a visible change to every session. User direction was to fix
the actual cause first and see whether that's enough. If clipping recurs,
this is the next lever.

### Verification

`npm run build` clean. Confirmed in the built output, not just the source:
`100dvh` and `env(safe-area-inset-top, 0px) + 8px` both present in
`dist/assets/phoneVerses-*.js` and `dist/assets/phoneVersesSandbox-*.js`, and
the `html, body { margin: 0; padding: 0; }` rule present in both dist HTML
files. No stale references to the v2.3 / v1.13 filenames remain in `src/` or
any HTML file.

**Not verified on a real device** — the fix addresses causes read from the
code, and whether it fully resolves the intermittent clipping needs phone
testing. See the "what's next" note above.

### Scope held back on purpose (Session 15)

Two adjacent issues were found this session and deliberately **not** bundled,
both recorded in `DEFERRED.md`:

- **The level-select back-button/title overlap** (new, reported this session
  with a screenshot). Held back so the header fix can be tested in isolation
  — bundling would make it impossible to tell which change caused any new
  behavior. Planned next.
- **The in-game title crowding the "See passage" button** — the session
  actually opened with this, and the analysis is preserved in `DEFERRED.md`.
  Set aside by the user mid-session in favor of the header fix. Note for
  whoever picks it up: the screenshot that prompted it was taken on a ~428pt

## Addendum — 2026-08-09 Session 16: vertical layout (phone-verses v2.5, sandbox v1.15)

Follow-on to Session 15. That fix stopped the header being clipped on the
reporting player's phone; this session made the vertical layout correct on
phones we can't test, and balanced the space on the one we can.

### The measurements everything rests on

Every band of a real 428×926pt screenshot was measured and scaled to CSS
pixels. **They sum to 927pt against a real screen height of 926pt** — that
agreement is why these are treated as measured rather than estimated, and any
future session revisiting this layout should re-derive from them:

| Band | Height |
|---|---|
| Space above header | 29pt |
| Header card | 94pt |
| Text bar (2 lines showing) | 67pt |
| Board container | 456pt (40pt tiles = `10 × tile + 56`) |
| Instructions panel | 72pt |
| Gaps between elements | 45pt |
| Dead space below | 86pt |
| **Usable page height** | **848pt** |

### The non-obvious finding

The instructions panel and the growing passage text bar compete for the same
space — but the panel (~118pt including its gap) is **nearly three times** the
text bar's total growth from one line to its four-line maximum (~42pt). So the
tallest moment of a round is its **beginning**, not its end, and the layout
gets *shorter* at move 2, not taller. That inverted the design problem: the
constraint is "does it fit at the start", not "will it still fit later".

### What shipped

1. **Vertical space rebalanced.** Wrapper padding was 8px top / 60px bottom.
   Centring happens *inside* the padding, so space above the content is
   `paddingTop + half the slack` and below is `paddingBottom + the same half`
   — that 52px difference was the entire cause of the game sitting high with
   dead space beneath it. Both are now 25px plus their safe-area inset, so the
   ~117pt of spare height splits evenly (~58pt each end). This **balances** the
   empty space rather than removing it; with the board size fixed it has to
   live somewhere. User chose the even split over spreading the slack between
   the elements.
2. **`justify-content: center` → `safe center`, feature-detected.** Plain
   centring splits overflow evenly above and below, and the half above the
   screen can't be scrolled to — the same class of failure Session 15 fixed,
   which would return on any phone too short for the layout. `safe` falls back
   to top-alignment on overflow, pushing it to the bottom where the least
   important content already sits. Feature-detected via `CSS.supports` into a
   module-level `SAFE_CENTER`, because a browser that doesn't know the keyword
   would drop the whole declaration and silently leave the game top-aligned
   even when there's room; the detection keeps those browsers on today's exact
   behavior.
3. **Instructions panel retires on short screens — by measurement.** New
   `hideInstructions` state plus a `useLayoutEffect` that compares the page's
   rendered height against `visualViewport.height` after every render. If the
   layout genuinely doesn't fit **and** the player has made two moves, the
   panel goes. On a phone with room to spare it never fires. `visualViewport`
   rather than `window.innerHeight` because innerHeight reports the
   toolbars-hidden height on iOS — the very mismatch behind the v2.4 bug. The
   two-move count reads `movesUsedRef` (incremented per successful swap, and
   not confused by bonus moves, which pin the regular move count at 0). Reset
   on restart; level changes remount the component and reset it for free.
4. **Height-aware tile size.** Tile size took the viewport width only. It now
   takes whichever of the width and height budgets is smaller.

### Decision recorded: don't hide the panel everywhere

The user caught a real flaw in the first proposal. Hiding the panel on *every*
phone would have freed ~118pt on a device that already had 86pt of dead space
at the bottom — trading a useful panel for a bigger band of empty background,
which is exactly the complaint that started the thread. Screen height decides
*whether* the panel is ever hidden; the move count decides *when*.

The agreed priority order when space is tight, in order: **keep the board as
large as the width allows → give up the instructions panel → shrink tiles.**
The board is the game and should be the last thing to give. `VERSES_CHROME_PX`
deliberately excludes the panel for exactly this reason.

### The one estimate, and why it's there

`VERSES_CHROME_PX = 350` is the only value in this work that isn't measured.
Tile size is locked at module load, before anything has rendered, so it can't
consult a measurement. Making it responsive would mean either resizing the
board after first paint (a visible jump) or turning `TILE_SIZE` into runtime
state, which every canvas draw call in a 7,700-line file reads — a refactor
out of proportion to the benefit. Being conservative costs nothing on any
phone where the width budget already binds, which is every phone larger than
the SE class.

### Expected effect by device

| Phone | Behavior |
|---|---|
| 428×926 (the reporting device) | Only the rebalanced padding is visible. Panel stays up all round, tiles stay at 40. |
| iPhone 15-class | Tiles unchanged; panel likely stays. |
| iPhone 13 mini | Tiles unchanged; panel retires at move 2. |
| iPhone SE-class | Smaller tiles **and** the panel retires; panel briefly clipped at the bottom for the first two moves (accepted by the user). |

### Verification

`npm run build` clean. Confirmed in the built bundles, not just source: the
`safe center` value, the symmetric `env(...) + 25px` padding, `visualViewport`
(8 property accesses), both resize listeners, both `offsetHeight` reads, the
inlined chrome constant, and the `v2.5` / `v1.15` in-game header labels.

**Only the first row of that device table is verifiable on hardware we have.**
The rest follow from the measured numbers. The mini and SE rows carry roughly
±40pt of uncertainty; the mini in particular was calculated to sit close to
the line. Narrowing and shortening a desktop browser window exercises the same
code paths and is the cheapest available check.

## Addendum — 2026-08-09 Session 17: level-select back button overlapped the title (phone-verses v2.6, sandbox v1.16)

Player-reported with a screenshot of Isaiah 52:13–53:12. On the **level-select
screen** (the per-level cards for a multi-level passage), the "← Back to
passage selections" button overlapped the passage title.

### Cause — a static collision, unrelated to Sessions 15 and 16

The back button is absolutely positioned at `top: 20px` and is 32px tall
(14px text + 12px vertical padding + 4px border), so it occupies the vertical
band **20–52px**. The title is a normal in-flow element, so it starts at the
container's **40px** top padding — 12px inside the button's band. The
container's top padding was never raised to account for a button that had been
taken out of the normal flow.

**It affected every passage, not just long-titled ones.** The button is ~212px
wide starting at x=20, so its right edge lands just past the middle of the
screen, and the title is centred — so every title crosses the button's column.
Isaiah only made it obvious because at 36px Georgia its capitals and digits are
tall enough to visibly cross the button's lower border.

Fix: container top padding **40px → 68px** (the button's 52px lower edge plus
~16px of breathing room).

### Bundled with approval: preventive safe-area padding on both select screens

Both select screens carried the same gap the game screen had before v2.4:
`viewport-fit=cover` runs the page under the iOS status bar, and when Safari's
bottom toolbar collapses to its pill the page shifts upward — so the top-left
controls (the back button here, the Tutorial pill on the passage-select
screen) could end up behind the clock and battery.

**This is preventive, not observed.** The reported screenshot was taken with
Safari's toolbar expanded, which is exactly the state where the page is *not*
shifted up. Recorded plainly so a future session doesn't mistake it for a
reproduced bug.

The important mechanical detail: **the inset had to be applied to the controls
themselves, not just their containers.** Raising a container's padding moves
in-flow content only — an absolutely positioned element is placed from the
container's edge and does not move. Both wrappers also went `100vh` →
`100dvh`, matching the game screen.

The passage-select screen's own 40px top padding is **unchanged**: its "Verses"
heading is short and sits well to the right of the Tutorial pill, so there was
no collision there — only the inset was added.

### Sandbox difference

The sandbox's passage-select screen has **no top-left control** — the Tutorial
was never ported to the sandbox — so that screen's container gained the inset
and there was no second control to adjust. Its level-select block was
character-for-character identical to phone-verses and got the full fix. Worth
remembering: the two files are near-identical but not identical, and a blind
find-and-replace port across them will fail (it did here, and the mismatch is
what surfaced the missing pill).

### Terminology

**"select", not "picker"** (user direction 2026-08-09). The code identifier
`VersesPicker` is unchanged — renaming it is deferred item 7. Two older lines
in `DEFERRED.md` still use "picker" and can be cleaned up whenever item 7 runs.

### Verification

`npm run build` clean. Confirmed in both source files and both built bundles:
no `100vh` remains in either platform file (3 × `100dvh` each — game screen
plus both select screens), the `+ 68px` container padding, the `+ 20px` button
inset, the `+ 40px` select-screen padding, the `+ 14px` Tutorial-pill inset
(phone-verses only, correctly absent from the sandbox), and the `v2.6` /
`v1.16` in-game header labels.

**Not verified on device.** The overlap fix is geometry and should be visible
immediately on any phone; the safe-area additions are preventive and by their
nature won't show a difference unless Safari's toolbar collapses.

## Addendum — 2026-08-09 Session 19: phone arcade tutorial + header parity (phone arcade v14.0)

### Why the phone arcade had no tutorial

Not a deliberate exclusion as far as the docs show — an omission. The
2026-07-04 build sequence read **tablet arcade → tablet-verses → phone-verses →
sandbox → campaign**. That list is verses-and-campaign shaped; the phone arcade
simply was never on it. The result was that the one platform teaching *pure
arcade play on a phone* was the one with no way to learn the rules, even though
its match mechanics are identical to tablet arcade's, which does have it.

Nothing in the archived progress docs explains the omission either way, so this
is inference rather than a recovered decision.

### The three changes, and how they connect

They look separate but are one chain:

1. **The tutorial button wanted the header's top-left slot** — tablet arcade's
   placement, and the only sensible spot, since the phone arcade drops you
   straight into a game and has no select screen to hang it on.
2. **That slot was occupied by the combo readout**, a 95px box showing a bare
   `🔥Combo x3` — blank most of the time, and cramped when not.
3. **So the combo moved to its own full-width row** at the foot of the header,
   mirroring tablet. That freed the slot *and* fixed a second problem: the
   phone version had been dropping the two things that make tablet's combo
   readout worth reading — the tier name (🔥 COMBO → 🌟 MEGA → ⚡ ULTRA →
   💥 LEGENDARY) and the points multiplier being earned.

### Why a taller header was the right call here

We had just spent two sessions recovering vertical space on the verses
platforms, so adding ~26px to a phone header deserved justification:

- **It can't clip anything.** Unlike the verses pages, this one is
  top-anchored (`justifyContent: 'flex-start'`) and already carried safe-area
  insets on all four edges, so the header was never at risk. Added height
  pushes content *down*.
- **The row is never empty.** Copying tablet's fallback — 🏆 high score and
  🔥 best combo when no combo is running — means the height is always doing
  something. It converts a slot that was blank most of the time into a line
  that always says something, rather than adding whitespace.
- **No new state.** `highScore`, `allTimeHighCombo`, `lastCombo`, and
  `getMultiplier` all already existed in this file and are in scope at render.
  The change is presentation only.

### Detail worth remembering: the target was icon-only

Removing the icons wasn't symmetrical. `⭐Score:` had a label under the icon,
so the star could simply be deleted. **`🎯3000` had no label at all** — the
icon *was* the label. Removing it would have left a bare number, so "Target:"
had to be restored. Anyone repeating this cleanup on another platform should
check for the same asymmetry before deleting an icon.

### Scope

`phone.html` gained the CSS reset and the wrapper went `100vh` → `100dvh`.
Neither was causing a visible fault here; both were included under the agreed
plan to fix the project-wide missing reset **per-platform, as each file is
touched for other reasons**. Approved before starting rather than bundled
silently. **Seven pages still carry the default body margin.**
