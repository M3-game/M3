## Addendum — 2026-05-01 N-6 phone-418-verses v1.3 responsive board sizing shipped

First session of 2026-05-01, opened with mid-conversation correction to the PROGRESS-doc rotation rule (CLAUDE.md + memory updated): rotation now happens when shipping on a date later than the current doc's date, not just because the day ticks over. This commit is the first to apply the new rule.

**Trigger.** User device-tested phone-418-verses v1.2 after N-5 ship (2026-04-29) and reported that the padding bump didn't visibly help on their phone — the ← back button and ☀️ theme toggle still felt pressed against the screen edge. v1.2 baseline confirmed correct via diff against v1.1 archive (all six padding/positioning edits were live), so the issue wasn't an unapplied edit. Stepping back, user asked about the production approach: "how would a real app handle this? Dynamically based on screen size?"

**Scoping pass (multi-message).** Three candidate paths surfaced:

- **A — Shrink to 9×10.** Simple, predictable, but shifts gameplay (one fewer column).
- **B — Keep 10×10 with smaller tiles.** Preserves grid dimensions / level data; smaller tiles may feel less precise.
- **C — Responsive scale.** Read viewport width at load, compute tile size at runtime. True production pattern; bigger code change.

User's instinct: "C seems best, but smaller boards on smaller phones might be hard to play. I'm leaning A+C." Math backed it up — A+C gives 36-42px tiles across the iPhone range; C alone bottoms out at 33px on iPhone SE (below Apple's 44pt tap target). 9×10 is industry norm (Candy Crush 9×9, Bejeweled started 8×8). Locked: **A+C**.

**User-broader question.** Mid-scoping, user asked whether this approach should eventually supersede phone-341 and phone-418 arcade — a single responsive mobile platform replacing the two fixed-width ones. Recommendation: yes eventually, but field-test on verses first (lower-stakes platform) before touching arcade. Two new deferred items logged in DEFERRED.md.

**Sub-decisions (one at a time):**

1. **Margin budget.** Standard 24px each side (48px chrome budget) — matches typical production iOS apps.
2. **Tile-size cap.** 40px (`MAX_TILE_PX`), matching tablet's tile size — preserves visual scale across platforms when a player switches devices. Without a cap, Pro Max gets 42px tiles which is marginally bigger but introduces cross-platform inconsistency.
3. **Chrome alignment.** Cards stay matched to `boardWidth` (Option B principle from N-5 preserved). Independent chrome breaks on small phones (chrome would be narrower than the board) — only viable on the largest phones, so not a real choice.
4. **Resize handling.** Lock tile size at module load; no resize listener. Verses platform is portrait-only in practice. Recomputing during animations adds risk for an edge case nobody asked for.
5. **Level target verification.** Defer recalibration. 10% fewer cells (90 vs 100) doesn't translate linearly to 10% harder targets — match-3 difficulty is non-linear. Playtest first, single-line tweak in a follow-up if needed.
6. **Session shape.** Ship N-6 as its own session before T-1, not bundled. The two changes are independent (responsive is structural, T-1 is mechanical); separate diffs are easier to revert independently. T-1 baseline now starts from v1.3 instead of v1.2.
7. **Scope.** Phone-418-verses only. Phone-418 arcade has the same chrome pattern but isn't reported as broken — speculative work right now. Logged as deferred for after verses is field-tested.

**Implementation.** Constants block updated at [match3-v1.3-phone-418-verses.jsx:768-865](platforms/phone-418-verses/match3-v1.3-phone-418-verses.jsx#L768-L865):

- `const COLS = 10` → `const COLS = 9`.
- `const TILE_SIZE = 40` (fixed) replaced by an IIFE that reads `window.innerWidth` once at module load, computes `floor((viewport - 2*TARGET_MARGIN_PX - (COLS-1)*TILE_GAP) / COLS)`, then clamps to `[20, MAX_TILE_PX]`.
- New constants surfaced: `TARGET_MARGIN_PX = 24` and `MAX_TILE_PX = 40`.

All downstream code (boardWidth derivation, canvas dimensions, hit detection, popup positioning, match detection) automatically picks up the new values via the existing `COLS`, `ROWS`, `TILE_SIZE`, `TILE_GAP` references — no other code edits.

**Per-iPhone math at runtime:**

| Phone | Viewport | TILE_SIZE | boardWidth | Margin/side | ← / ☀️ from screen edge |
|---|---|---|---|---|---|
| iPhone SE | 375px | 34 | 322px | 26.5px | ~42px |
| iPhone 12-15 | 390-393px | 36 | 340px | 25-26.5px | ~41-42px |
| 418px reference | 418px | 39 | 367px | 25.5px | ~41px |
| iPhone Plus / Pro Max | 428-430px | 40 (capped) | 376px | 26-27px | ~42-43px |

iPhone's rounded screen corner is ~24-30px on current production devices. Buttons clear that with ~10-15px to spare on every phone in the range.

**Build verification.** `npm run build` clean, 66 modules transformed, zero warnings. `phone418Verses` bundle 78.14 kB / 23.56 kB gz (was 77.99 / 23.49 in v1.2; +0.15 kB from new comment block + IIFE).

**Inherited TypeScript "hint" diagnostics** still present (the 9 unused-var hints inherited from v1.7 → v1.8 → v1.0 → v1.1 → v1.2). Out of scope for N-6.

**Process notes.**

## Addendum — 2026-05-01 T-1 bundled terminology rename shipped (3 of 8 platforms)

Second session of 2026-05-01, ran after N-6 in the same day. Tablet v11.13 → v11.14, tablet-verses v1.9 → v1.10, phone-418-verses v1.3 → v1.4. One commit covers all three platforms + docs (per locked decision #7). Implementation order followed locked instruction: tablet first, then tablet-verses, then phone-418-verses.

**Mid-session decisions.** Three discoveries surfaced during execution that the original locked scoping didn't anticipate. Each surfaced organically as the rename proceeded; in each case I paused and presented options before continuing.

1. **Stats data layer (`endType: 'bonusRound'` + `stats.bonusRoundsTaken`) — Option A.** Discovery: `recordGameResult()` writes the literal string `'bonusRound'` into the `match3_stats` localStorage blob's per-game history, and increments a counter `stats.bonusRoundsTaken` read by AdminPanel for display. Neither is on the original T-1 inventory. Three options surfaced: A (leave alone — preserves locked decision #5 "core stays unchanged"), B (rename without migration — counter visibly resets to 0), C (migrate — but stats blob is shared across 8 platforms via core; the deferred 5 still write old strings, so any rename either touches core+all 5 or creates ugly ping-pong migration). User chose A; matches Option A's "leave the data layer alone in T-1; full sweep handles it later" spirit. Net effect: AdminPanel's per-game history shows old `'bonusRound'` for historical entries; counter keeps incrementing under the old name. Cosmetic-only mismatch in a power-user surface.

2. **Two missing-from-inventory rename targets — `onBankedMovesChange` callback prop + hyphenated `banked-moves` comment form.** Discovered during the tablet-verses pass. The verses-pattern uses an inner `Match3Game` component receiving a callback prop `onBankedMovesChange` from the wrapper; my identifier rename caught the local setter `setBankedMoves` it gets bound to (now `setBonusMoves`), but the prop name itself wasn't in the inventory. Same situation in phone-418-verses. Also surfaced: hyphenated comment text `banked-moves` (e.g., `// banked-moves prompt`) didn't match my space-separated `banked moves` text rename. User approved adding both to T-1 to avoid the "half-finished implementation" anti-pattern. Renames applied to both files: `onBankedMovesChange` → `onBonusMovesChange`; `banked-moves` → `bonus-moves` (and `Banked-moves` → `Bonus-moves` for the capitalized variant).

3. **Phone-418-verses cross-platform key share — storage VALUE preserved.** Discovered during the phone-418-verses pass. The constant `PHONE418_BANKED_MOVES_KEY` declares its storage string as `'match3_phone418_bankedMoves'` — the SAME string used by phone-418 arcade's own `BANKED_MOVES_KEY` constant (in `platforms/phone-418/match3-v13.2-418px-phone.jsx`). The two files intentionally share one localStorage key for the bonus-moves pool, and the verses → arcade carry-out flow at line ~5491 writes to it so arcade can pick up the merged total on entry. Original locked decision #2 ("rename + migrate") didn't anticipate this share — would have written verses' new key to disk while arcade still read the old key, breaking the carry-out. Resolution: rename the constant *name* in T-1 (`PHONE418_BANKED_MOVES_KEY` → `PHONE418_BONUS_MOVES_KEY`) for code coherence, but KEEP the *value* as `'match3_phone418_bankedMoves'`. No migration needed (no on-disk change). The future cross-platform sweep migrates both constants in lockstep — captured as a hard requirement in `DEFERRED.md` "Cross-platform terminology sweep" entry, with an in-code reminder block at the constant declaration in v1.4.
