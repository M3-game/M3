## Addendum — 2026-05-01 N-6 phone-418-verses v1.3 responsive board sizing shipped

First session of 2026-05-01, opened with mid-conversation correction to the PROGRESS-doc rotation rule (CLAUDE.md + memory updated): rotation now happens when shipping on a date later than the current doc's date, not just because the day ticks over. This commit is the first to apply the new rule.

**Trigger.** User device-tested phone-418-verses v1.2 after N-5 ship (2026-04-29) and reported that the padding bump didn't visibly help on their phone — the ← back button and ☀️ theme toggle still felt pressed against the screen edge. v1.2 baseline confirmed correct via diff against v1.1 archive (all six padding/positioning edits were live), so the issue wasn't an unapplied edit. Stepping back, user asked about the production approach: "how would a real app handle this? Dynamically based on screen size?"

**Scoping pass (multi-message).** Three candidate paths surfaced:

- **A — Shrink to 9×10.** Simple, predictable, but shifts gameplay (one fewer column).
- **B — Keep 10×10 with smaller tiles.** Preserves grid dimensions / level data; smaller tiles may feel less precise.
- **C — Responsive scale.** Read viewport width at load, compute tile size at runtime. True production pattern; bigger code change.

User's instinct: "C seems best, but smaller boards on smaller phones might be hard to play. I'm leaning A+C." Math backed it up — A+C gives 36-42px tiles across the iPhone range; C alone bottoms out at 33px on iPhone SE (below Apple's 44pt tap target). 9×10 is industry norm (Candy Crush 9×9, Bejeweled started 8×8). Locked: **A+C**.

**User-broader question.** Mid-scoping, user asked whether this approach should eventually supersede phone-341 and phone-418 arcade — a single responsive mobile platform replacing the two fixed-width ones. Recommendation: yes eventually, but field-test on verses first (lower-stakes platform) before touching arcade. Two new deferred items logged in DEFERRED.md.

**Sub-decisions (one at a time):**

1. **Margin budget.** Standard 24px each side (48px chrome budget) — matches typical production iOS apps.
2. **Tile-size cap.** 40px (`MAX_TILE_PX`), matching tablet's tile size — preserves visual scale across platforms when a player switches devices. Without a cap, Pro Max gets 42px tiles which is marginally bigger but introduces cross-platform inconsistency.
3. **Chrome alignment.** Cards stay matched to `boardWidth` (Option B principle from N-5 preserved). Independent chrome breaks on small phones (chrome would be narrower than the board) — only viable on the largest phones, so not a real choice.
4. **Resize handling.** Lock tile size at module load; no resize listener. Verses platform is portrait-only in practice. Recomputing during animations adds risk for an edge case nobody asked for.
5. **Level target verification.** Defer recalibration. 10% fewer cells (90 vs 100) doesn't translate linearly to 10% harder targets — match-3 difficulty is non-linear. Playtest first, single-line tweak in a follow-up if needed.
6. **Session shape.** Ship N-6 as its own session before T-1, not bundled. The two changes are independent (responsive is structural, T-1 is mechanical); separate diffs are easier to revert independently. T-1 baseline now starts from v1.3 instead of v1.2.
7. **Scope.** Phone-418-verses only. Phone-418 arcade has the same chrome pattern but isn't reported as broken — speculative work right now. Logged as deferred for after verses is field-tested.

**Implementation.** Constants block updated at [match3-v1.3-phone-418-verses.jsx:768-865](platforms/phone-418-verses/match3-v1.3-phone-418-verses.jsx#L768-L865):

- `const COLS = 10` → `const COLS = 9`.
- `const TILE_SIZE = 40` (fixed) replaced by an IIFE that reads `window.innerWidth` once at module load, computes `floor((viewport - 2*TARGET_MARGIN_PX - (COLS-1)*TILE_GAP) / COLS)`, then clamps to `[20, MAX_TILE_PX]`.
- New constants surfaced: `TARGET_MARGIN_PX = 24` and `MAX_TILE_PX = 40`.

All downstream code (boardWidth derivation, canvas dimensions, hit detection, popup positioning, match detection) automatically picks up the new values via the existing `COLS`, `ROWS`, `TILE_SIZE`, `TILE_GAP` references — no other code edits.

iPhone's rounded screen corner is ~24-30px on current production devices. Buttons clear that with ~10-15px to spare on every phone in the range.
