## Addendum — 2026-08-22 Session 20: escalating target survives navigation (tablet arcade v12.1)

### The bug, and why it was wider than reported

Reported as "switching from verses to arcade resets the target score." The
cause was that `difficultyBonus` — the accumulated raise applied to each new
round's target — was ordinary React state initialized to 0. Both cross-mode
buttons are full page navigations (`window.location.href`), so the whole app is
torn down and the accumulation discarded.

**It was never specific to the verses round trip.** A refresh, a closed tab, or
returning the next day did exactly the same thing. The v12.0 "Go to Verses"
button simply made an existing gap visible by giving players a routine reason to
leave and come back mid-session.

**What made it read as broken rather than merely forgetful** is that the run
counter *was* already persistent (`match3_currentRun`). So after a round trip the
game could report a six-win run beside a beginner target — two features visibly
disagreeing.

### The trap in the fix

Persisting the value is about ten lines, but there are **two** places the target
gets computed. `restartGame` had always added `difficultyBonus`; the initial
`useState` for `levelTarget` deliberately did not, which was correct only while
the value was guaranteed to be 0 at mount. Fixing just `restartGame` would have
left the first round after every page load at the base target with the ramp
appearing on round 2 — the bug half-present, in a form easy to mistake for fixed.

### Design decisions taken during scoping

The fix itself is small; most of the session was design. Recorded in full in
`DESIGN.md` → "Escalating Target (Arcade)" and `DEFERRED.md` → "Reward levels".
The short version, with the reasoning that isn't obvious from the outcome:

- **Permanent persistence, not per-session.** Chosen because the run counter is
  already permanent; a session-scoped target would have produced the same
  contradiction one day later instead of one navigation later.
- **Uncapped, but tapering.** No ceiling; the loss reset is the real limiter.
  The taper stops difficulty accelerating as a run gets long.
- **Boundaries at 12/24/36 rather than 10/20/40** purely so tier steps never
  coincide with the planned every-5-wins reward levels. On 10/20/40 every
  boundary collided; with 12 the first coincidence is win 60.
- **A 100 floor on the later bands**, because the target rounds to the nearest
  100 and smaller increments would be invisible. This also caps how flat the
  curve can ever get — a discovery that killed a proposed fifth, gentler tier.
- **"Highest target reached", not "beaten".** User direction: "beaten" reads as
  gamer-speak. "Reached" also reuses vocabulary the game already teaches on its
  win banner. Semantics are the same — the highest target actually achieved, so
  the round that ends a run does not count.

### Two proposals that were reversed during the session, and why

Worth recording so they aren't re-proposed:

1. **"Highest target reached" on the in-game header, beside high score.** Killed
   on a structural finding: **high score is always ≥ highest target**, because
   winning requires scoring at least the target. Side by side the new stat would
   be permanently the smaller number with no visible reason why, reading as a
   weaker duplicate of the stat next to it. It went to the end screen instead,
   grouped with the run stats where it belongs — it is a run achievement.
2. **A persistent in-game marker on record-breaking rounds.** The target is fixed
   for a whole round, and once a run passes its own best *every* later round
   qualifies — so the badge would light up and never go out for the rest of the
   run. The user's fix (show it ~5 seconds at round start, then clear) restores
   it to being an event, and is now what shipped.

### The stat that turned out not to be redundant

An early concern was that "highest target reached" duplicated "longest run" —
both climb on a win, both reset on a loss. That objection dissolved once reward
levels were scoped: reward wins count toward the run but **not** toward the ramp,
so longest run counts every win including the easy ones, while highest target
only moves on arcade rounds. They now measure genuinely different things: how
long you kept going, versus how hard a fair round you beat.

### Note on the tier lookup and reward levels

The tiers currently key off `currentRun`, which is correct **only while every win
is an arcade win**. Once reward levels count toward the run, the tier lookup will
need its own count of arcade wins or the boundaries will trip early. Flagged in
`DEFERRED.md`; not built, because a second counter identical to the first would
be speculative today.

### Scope held back on purpose

- **Phone arcade has the identical bug** (`match3-v14.0-phone.jsx:1174`). Not
  bundled — whether phone also takes the tiers and the new stat is its own
  decision.
- **`#888` in the tablet header stat row**, below the project's #ccc contrast
  floor on dark backgrounds. Noticed while adding the marker; recorded, not
  touched.

### Verification

`npm run build` clean. Confirmed in the built bundle (`dist/assets/tablet-*.js`),
not just source: `match3_difficultyBonus`, `match3_highestTarget`, "Highest
target reached", "Highest target yet", the `targetRecordFade` keyframes, and the
`v12.1` label. No `DIFFICULTY_INCREMENT_*` constants remain, all four win paths
call `difficultyIncrementFor(currentRun + 1)`, and no stale `v12.0-tablet`
references remain in `src/` or any HTML file. Tier boundaries were checked
against a standalone script: wins 1/11 → 200–500, 12/23 → 200–400, 24/35 →
100–300, 36/50 → 100–200.

**Not verified by playing.** The persistence fix is straightforward and the
build confirms the wiring, but the 5-second marker's timing and colour on the
real header, and the end-screen line's placement, have not been seen running.

## Addendum — 2026-08-22 Session 21: bonus-moves cap divergence (rewardmode v1.5, tablet-sim v1.6)

### The bug

Player-reported: arriving in the reward-mode sandbox from arcade with more than
99 bonus moves and then playing reduced the total to 99, and that reduced number
followed the player back into arcade and verses.

All platforms read and write **one** stored count (`match3_bankedMoves`), so the
cap has to be identical in every file. Tablet v11.17 raised it 99 → 999 — and
that comment in the tablet file explicitly warns that a mismatch "would knock a
>99 pool back to 99", which is exactly what happened.

### Why the v11.17 bump missed two files

**A naming split, not a decision.** The T-1/T-2 terminology work renamed
`BANKED_MOVES_CAP` → `BONUS_MOVES_CAP` on most platforms. The reward-mode
sandbox and Tablet Sim were never renamed — the rewardmode file says so
explicitly in its header ("rewardmode is a dev sandbox; full terminology
[rename deferred]"). The v11.17 bump was then applied by searching for the *new*
name, so both files kept the old name and the old value.

### The detail that explains why the sandbox seemed safe

Nothing is lost on arrival. The stored count is read as-is
(`match3-v1.4-tablet-rewardmode.jsx:1504`) and written back as-is (`:1814`). The
cap is applied **only on earning** — `Math.min(prev + newMoves, CAP)` at `:1932`
— so the loss fires at the first 10,000-point threshold reached in the sandbox,
and the persistence effect immediately saves the reduced number for everything
else to read.

Tablet Sim carries the identical code (`:2140` earn clamp, `:2022` write) and was
fixed in the same session before anyone hit it.

**Desktop v12.3, Time Attack v12.4 and Campaign v1.28** all touch the shared
count but define no cap at all, so they cannot reduce it. Safe, but recorded as
its own inconsistency.

### Deferred: move the constant into `core/`

The hand fix closes this instance; the class of bug survives, because the same
limit is written out in seven platform files under two names. `core/` is
edit-in-place and imported by all of them, so one exported constant would make
divergence structurally impossible. User approved in principle and chose to
defer. See DEFERRED.md → "Cross-platform parity".

### Note on the player's save state

The lost moves are unrecoverable — nothing recorded the prior value. The user
declined restoration, noting the surplus only existed because the pre-v12.1
target reset made rounds easy to win repeatedly. **Their `match3_currentRun` is
now over 100**, which interacts with the v12.1 tiers — see the caveat below.

### Verification

`npm run build` clean. Confirmed in both source files and both built bundles:
`BANKED_MOVES_CAP = 999` and `BANKED_MOVES_WARN = 900`, the `v1.5-sandbox` and
`v1.6` in-game labels, and no stale references to the previous filenames in
`src/` or any HTML file. The "Nearing cap — max N" message reads the constant,
so it corrected itself.

**Not verified by playing.** The fix is two constants; the build confirms they
reach the bundles.

## Caveat carried into the next session — a 100+ win run meets the v12.1 tiers

Surfaced 2026-08-22 after v12.1 shipped. The tier lookup picks the increment
band from the current run length, and this player's `match3_currentRun` is over
100 because the pre-v12.1 target reset made rounds repeatedly winnable. So they
sit in **tier 4 (36+ wins, 100–200 per win)** — the gentlest band — while their
`match3_difficultyBonus` starts from roughly zero, since it was never persisted
before v12.1.

The practical effect is that the target will climb about as slowly as the design
allows, from a base start, for a player the game believes is 100 wins deep. Not
a code fault — the tiers are behaving exactly as specified — but the specified
behavior assumes the run counter and the accumulated bonus grew together, which
was never true for data created before v12.1.

**Decision (user, 2026-08-22): leave it and let the run play out.** This is a
beta test run, and a single loss resolves the mismatch on its own — the loss
path zeroes `difficultyBonus`, and `restartGame` zeroes `match3_currentRun` on
the next round. From that point both counters grow together and the tiers
behave exactly as specified. No code change, no manual storage edit.

Two alternatives were considered and rejected: resetting `match3_currentRun` to
0 by hand, and seeding `match3_difficultyBonus` to roughly what a 100-win run
would have accumulated.

**What to expect in the meantime:** a base-level target with the gentlest
increments (100–200 per win), so rounds stay comfortably winnable and the first
loss may be a long way off. The tier behavior worth testing — the taper, and the
step at 12 wins — will not be observable until after that loss and a fresh
climb. A future session reading this should not mistake the slow climb for the
persistence fix having failed; the check for that is whether the target survives
a trip to verses and back, not how fast it rises.
