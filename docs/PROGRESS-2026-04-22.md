## Narrative summary — what we've discussed and decided

Running record of substantive conversation threads whose conclusions aren't
directly reflected in another doc. This section is written for someone (or a
future session) picking up cold.

### iOS Safari storage purge — the real cause of "lost progress"

Early suspicion during Session A planning was that stats persistence was
broken. Turned out the localStorage keys are version-agnostic and don't reset
between versions. The real culprit is **iOS Safari's 7-day ITP storage
purge** — Safari auto-deletes localStorage for sites the user hasn't
interacted with for 7 days. Since the M3 site is hosted on GitHub Pages
(`m3-game.github.io`) and the user primarily plays on iPad, stats were
vanishing on a weekly cadence.

Fixes considered:

- **Manual export/import** (shipped in Session A for campaign): user can
  copy backup JSON to clipboard or download a file; paste back to restore.
  Low-friction safety net.
- **PWA install ("Add to Home Screen")** — reduces purge risk on iOS but
  doesn't eliminate it. Blocked on real icon assets.
- **IndexedDB migration** — some protection but iOS eventually purges it too.
- **Backend sync (Firebase etc.)** — full fix but adds ongoing maintenance
  + cost.

Decision: ship the manual export/import now; escalate only if the backup is
still being lost. PWA install is in DEFERRED.md pending icon assets.

### Phone-418 "bonus moves never prompt" was actually a deploy bug

User reported during Session C planning that phone-418 earns bonus moves
but never shows the prompt. Code audit concluded the logic was correct.
Cache-busting didn't help. The real issue: **`vite.config.js` had the
phone-418 rollup input pinned to `v11`** — so v12.0, v12.1, v12.2 all
committed in the source tree but never made it into `dist/` during build.
The user had been playing v11 the whole time. One-line fix (Session B).

Followup in DEFERRED.md: auto-copy all phone-418 versions into `dist/`
(via `public/` directory or `vite-plugin-static-copy`) so this class of
bug can't happen on future bumps.

### Tablet hypernova — audit found parity, user then wanted behavior change

Session C started as an audit task: "does the tablet hypernova match the
campaign's?" The audit concluded **yes, they're functionally identical**
(both solo and combo). The user realized their mental model ("solo hypernova
leaves half the board + all specials; combos should feel similar") diverged
from the existing code: specifically, hypernova combos were clearing all
non-specials (close to whole-board wipe), not "two footprints + half of
rest."

The user then made a **design decision** that the combo behavior should
change — and that solo hypernova should *also* fire specials caught in its
footprint (previously it skipped them). Session C implemented both changes.

This crystallized into a broader design principle — **"Variety through
amplification, not interference"** — which was added to `DESIGN.md`.
Skilled play involves setting up specials for future cascades; the game
shouldn't disrupt that planning by nuking everything.

### Skilled play is deeper than the simulation bots we'd initially planned

Originally scoped Session E as a simple 1-ply heuristic bot (pick best
immediate move by match length / special-creation). In discussion the user
clarified: skilled play is often 5–8 move lookahead — setting up a special
next to another special, aligning cascades across rows, queuing up a
mega-combo six moves out. A 1-ply bot captures none of that.

Consequence for Session E: treat 1-ply results as **lower-bound casual
play**, *not* as a calibration target. If the bot finds levels too hard,
that doesn't mean the levels *are* too hard. Monte Carlo (v3) or 2-ply
lookahead (v2) are closer to skilled play; human-replay capture is the
best ground-truth anchor.

This conversation also shaped the Reward-mode design: simulation should
happen *before* sandbox tuning so we can compare empirical difficulty-vs-
lever-setting curves, not guess.

### Commercial match-3 monetization mechanics are explicitly rejected

Ice, stone, jelly, locked tiles, and similar obstacles exist in most
commercial match-3 games because they extend time-to-engagement and
create monetization touch-points (boosters, extra moves for a fee,
time-skip payments). The user doesn't monetize; these mechanics reliably
make them put the game down. Captured in DESIGN.md as a narrow
exception-only policy for a hypothetical future long-form campaign
(<10% of levels, explicit marking, never default).

### "Match-3 literature" — there is no venerable tome

Clarification during a side discussion: I'd casually called published
match-3 research "literature" as if it were an established body. It isn't.
Scattered academic papers (FDG, AIIDE, IEEE CIG/COG, KDD) exist; King has
published some data-science work on Candy Crush level difficulty; Julian
Togelius and a few others touch match-3 in the broader game-AI space.
No coherent survey paper. Best "literature" is reverse-engineering shipped
games.

User parked a multi-session research task for when tokens are fresh —
three focused queries (difficulty prediction, bot architectures,
amplification-vs-interference design patterns), including monetization
research as foreign-perspective reference. See DEFERRED.md.

### "Specials fire in the footprint" was a genuine solo-hypernova change

During Session C planning the user said "I think hypernova should fire
specials in its footprint/zone, is that not what you're proposing?" —
but in fact the existing solo hypernova skipped specials entirely.
Changing solo hypernova to fire specials in its footprint (in addition
to changing the three combos to do the same) was a meaningful behavior
shift, not just a code cleanup. Both were shipped in Session C.

User's question and the clarification that followed illustrated a
useful pattern: the user's mental model of how the game *should* work
sometimes diverges from how it actually works today, and the audit is
what surfaces it. Design reviews are load-bearing.

### Session boundaries + commit discipline

Emergent pattern across sessions:

- Each session has a version bump on at most one platform file (A: campaign,
  C: tablet, D: tablet).
- Docs updates bundled with the session's code where possible, or shipped
  as a separate small commit right before.
- Pause points honored — "stop" / "pause" messages aren't questions, they're
  commands. State-on-disk summary at pause helps resume cleanly.
- End-of-session commits include detailed body text describing what
  changed and why; session number/scope in the subject line.
- TodoWrite used to track multi-step sessions; cleared between sessions.

### Session letters and naming

Sessions are labeled A, B, C, D, D-2, E, F, G, H, I, plus "Research."
Letters assigned roughly in the order the session was scoped, not
strictly by ship order. Session B's phone-418 deploy fix was a

## Addendum — Session J-port shipped (phone-418 campaign parity + run tracking)

Port of tablet v11.9 features to phone-418, plus a small layout
restructure that bundled cleanly with the work.

**Port coverage** (all four pieces from tablet v11.9):
1. `BANKED_MOVES_CAP = 99` + `BANKED_MOVES_WARN = 90` constants; the
   bonus-move award path (in the scoring useEffect) now clamps with
   `Math.min(prev + newMoves, CAP)`. Header text turns amber at ≥WARN
   with "Nearing cap — max 99" subtext; turns red at CAP with "Cap
   reached — no additional moves can be earned". Moves earned past cap
   are silently dropped (flash still fires — matches tablet).
2. Run tracking with phone-418-scoped keys (`match3_phone418_currentRun`
   / `…_longestRun`) — deliberately separate from tablet's
   `match3_currentRun` / `match3_longestRun` so iPad and iPhone have
   independent runs. A useEffect on `gameState` increments on 'won' and
   persists both keys; 'gameover' preserves currentRun so the end-game
   banner can show the broken run. `restartGame` resets currentRun if
   the previous game was a loss.
3. `requestEndGameCarryBanked` wrapper on the in-header End-and-carry
   button: runs `calculateUnusedSpecialsBonus` against the same
   would-win logic `endGameCarryBanked` uses, so it only fires the
   confirm when the player is ACTUALLY below target (not just below
   before specials bonus). The confirm popup uses the same orange
   gradient as tablet but with tighter phone-sized padding.
4. End-game banner: run tracking display added between the Final Score
   line and the details column. Shows "Current run: N wins [🏆 new
   best!]" on win; "Run broken at N wins" on loss (or "No active run"
   if currentRun=0 at loss); always shows "· Longest run: N".

**Banner restructure** (user request, bundled):
The Score/Moves/Target row was a single flex row with `justify-content:
space-between`. The inline "Bonus moves: N" span inside the Moves div
was too wide for phone-418's 418px viewport and the browser was
soft-wrapping it so the number landed below "Moves: N". Fix: closed the
flex row after Target; "Bonus moves: N" (with cap messaging when
applicable) is now a separate row below the flex row, as a sibling
child of the outer HUD container. The bonusRoundActive banner and the
usingBankedMoves End-button also moved out of the flex row as siblings
— they render the same visually (they had `marginTop: '6px'`) but
they're now proper block-level rows instead of flex children. Net: one
`)` moved from the end of the bankedMoves button chain UP to just
after Target, with the new bonus-moves row inserted between.

Header title also bumped v12.0-418px → v12.4-418px (was stale; phone
equivalent of the tablet banner still showing v11.2).

**Verification**
- `node --check` on extracted v12.4 script: clean
