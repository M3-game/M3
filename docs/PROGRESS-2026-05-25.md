12 verses games (28 levels total). Standalone read-only analysis;
no code changes. Findings:

- N = 28 levels.
- Min = 7 moves (2 Chronicles 7:14). Max = 28 moves (Matthew 5:38–48).

### The four in-session items

**#7 — 1 Thessalonians card font shrink.** Picker and level-select
card titles longer than 20 characters render at 16 px instead of
18 px. Today the threshold catches only "1 Thessalonians 4:13–18"
and its two level titles. Length-based check (not slug-specific)
so future long titles auto-shrink. Three fontSize sites changed in
each platform (picker card title, locked level-select card, unlocked
level-select card). User's stated fix was "reduce slightly"; Claude
offered the alternative of abbreviating the title to "1 Thes. 4:13–18"
(matching the in-game reference column abbrev); user chose to keep
the full title and reduce the font instead.

**#1 — Biblical-order card sort.** Picker now iterates games in
canonical Protestant Bible order rather than slug-alphabetical.
Three implementation paths offered (slug-order array, per-game
`order: N` number, per-game `book` + `chapter` fields with a
canonical book list in shared core). User chose the third
("path 2 is the right choice for now and future additions") for
zero-friction onboarding of future games. Implementation:

- New shared file `core/versesOrder.js` — exports `BIBLE_BOOKS`
  (66-book Protestant canon, OT + NT in order) and
  `sortVersesSlugs(registry)`. Per-platform copies of the registry
  pass into this function and get back an ordered slug array.
  Edit-in-place core file (no versioning, per CLAUDE.md core
  exception).
- 12 game.js files in `content/verses/*` each gained a `book`
  (string) and `chapter` (number) field. Psalm 23 + Psalm 91
  both declare `book: "Psalms"` (canonical plural even though
  slugs are `psalm-23` / `psalm-91`).
- `content/verses/_template/game.js` updated with placeholder
  `book` + `chapter` fields and a comment pointing at
  `core/versesOrder.js` for the canonical book list.
- Each platform's `VersesPicker` component signature changed:
  was `({ games, progress, onPick })` → now
  `({ games, slugs, progress, onPick, ... })`. Caller passes the
  module-level `versesGameSlugsOrdered = sortVersesSlugs(versesGameRegistry)`.
- Verified via standalone Node sort that the 12 games produce
  Genesis 1 → 1 Peter as expected.

**#3 — Target-score tuning (sandbox only).** Per-level target formula
split on move count: `moves < 17 → moves × 300`, `moves ≥ 17 → moves × 500`.
Replaces v1.4's uniform `moves × 1000`. Threshold of 17 chosen because
of the natural gap in the level-length distribution (no levels currently
fall at 15–16 moves). Old constant `TARGET_PER_MOVE_DEFAULT = 1000`
replaced by `TARGET_PER_MOVE_THRESHOLD / SHORT / LONG`. User's original
ask was `× 250 / × 500`; revised mid-scope to `× 300 / × 500` after
Claude flagged that main phone-verses already uses × 250 (uniform) and
tablet-verses uses × 300 (uniform), so × 300 for the short bucket
matches tablet-verses precedent. Main platforms unchanged for now —
revisited at item #6 (sandbox → main port) when sandbox mechanics
converge into main.

**#2 — Secret-unlock long-press.** 1.5 s long-press on either the
"Verses" picker header or any game-title level-select header toggles a
global `m3_verses_secret_unlock` flag in localStorage. When ON, every
locked level in every multi-level game becomes clickable — bypassing
the normal "complete L1 to unlock L2" progression. When ON, both
headers gain a 🔓 prefix as a visible indicator. Long-press timer
parameters match the existing AdminPanel gesture (1500 ms,
`onPointerDown` to start, `onPointerUp` / `onPointerLeave` to clear).
Implementation in each platform: state lives in the outer
`Match3Verses` wrapper, passed as `secretUnlock` + `onSecretPressStart`
+ `onSecretPressEnd` props to both `VersesPicker` and
`VersesLevelSelect`. `isUnlocked(idx)` short-circuits to `true` when
the flag is ON. User asked about gesture surface mid-scope; Claude
proposed level-select-only (where locks actually exist), user added
"global unlock through the Verses header would also be good" → both
headers gained the gesture.

## Addendum — 2026-05-25 #8 sandbox nova-drop turn-boundary fix

Second ship of the day, following the morning four-item batch
(commit 57614e7). User picked up TODO #8 (nova-drop timing fix,
sandbox first then main) for the next scoping pass.

### The bug, in player terms

The user described the bug clearly in player-experience terms after
catching me framing it from the code's perspective:

> A turn is one player match plus everything that follows from it
> — cascade, falling tiles, all the refills — until the board is
> fully settled. One event with a clear start (player makes a match)
> and a clear end (board settled).

> A big turn happens. Player sees the "big turn" banner. Lots of
> tiles fall, including the nova that the banner announced. (This
> is still the same turn — and if the code thinks differently, the
> code needs to change.) Next turn: player matches 3 tiles
> horizontally. Tiles fall, three new tiles drop, but no nova drops.
> From the player's view, the game lied.

The popup ("Hypernova drops on your next move") promised a nova on
the next move and didn't deliver. Whatever the exact code path, the
nova was landing in the trigger turn's own refills instead of the
player's next match.

### Fix shape

Added a "ready gate" flag (`_pendingSpecialDropReady`) next to the
existing module-level `_pendingSpecialDrop` queue:

- Default state: closed.
- Opens only at the start of the player's next `attemptSwap`, and
  only if a drop is queued.
- `fillEmptySpaces` consumes the queue only when the gate is open;
  closes the gate immediately on consume.
- Same logic applies to both Mechanic B (big-turn drop) and Mechanic
  C (floor-raise rescue drop) since they share the same queue.

Net effect from the player's seat: the popup's promise is reliably
true. The nova lands in the first refill of the player's next match,
even if that next match is the simplest possible (3-tile clear with
3 new tiles falling).

### Bias-spike edge case discovered, NOT fixed in v1.6

During investigation, I traced Mechanic C's bias-spike timing and
found a pre-existing edge case:

The spike transfers from `pendingBiasOverridePctRef` →
`biasOverridePctRef` at the end of *every* turn-complete cycle. If
the player makes an invalid swap (no-match swap-revert) between the
trigger turn and the consume turn, the spike gets wiped before the
consume turn's fill cycle reads it. The drop itself still lands on
the right turn under the gate fix; only the placement-help bias is
lost. The rescue special can land in a barren patch.

The cleanest fix interacts with Mechanic D's mid-turn hypernova-
suppression logic (Mech D also writes to `biasOverridePctRef`, and
the end-of-turn wipe is intentional for Mech D). User chose to ship
v1.6 with the gate fix only and capture the bias-spike fix as a new
TODO item (#12) for a follow-up scoping pass.

Also captured as a dependency of TODO #6 (sandbox → main port).
Porting Mech C to main without #12 would carry the same bug to main.
