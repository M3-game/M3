## Addendum — 2026-07-04 Session 5: tutorial port to phone-verses (v2.0) + responsive scaling

Second tutorial port, same day. Two pieces:

- **`core/Tutorial.jsx` (edit-in-place) — responsive scaling.** The modal has a
  fixed natural size (the demo board is a fixed-pixel canvas), which fits a
  tablet but overflows a phone. Added a measure-and-scale step: a `useLayoutEffect`
  reads the box's natural (un-transformed) `offsetWidth/Height` and sets a CSS
  `transform: scale(...)` so the whole box fits `window.innerWidth/Height`
  (recomputed on resize + per panel, since panel heights differ). On wide screens
  the scale is 1, so tablet arcade + tablet-verses are visually identical and
  need no version bump (they inherit the core edit). The overlay got
  `overflow: hidden` so the scaled box never creates scrollbars.

  add the opt-in "Tutorial" link at the top-left of the passage-selection screen,

## Addendum — 2026-07-04 Session 6: verses bug fix (v2.1 / v2.1 / v1.11)

Two player-reported bugs turned out to be one root cause. Fixed on all three
verses platforms: tablet-verses v2.0 → v2.1, phone-verses v2.0 → v2.1,
phone-verses-sandbox v1.10 → v1.11. Patch bumps (bug fix, no gameplay/scoring
change).

### The two symptoms
1. **First line reveals, second line doesn't after the first move.** Only the
   first move was affected — later moves revealed lines normally.
2. **Single-level game freezes at 0 moves** — the end-of-round passage modal
   never appears.

### One root cause
Lines reveal one at a time as moves are spent; the reveal effect detects a spent
move by comparing the current move count to `prevMovesRef` (the previous count).
The "Begin game" handler (and the "Play again" restart path) reset
`prevMovesRef` to `null` **and** called `setMoves(versesLevel.moves)`. But at
Begin-click time `moves` already equalled `versesLevel.moves` (seeded by the
mount initializer, or by restart) in the default 1× case — so `setMoves` was a
no-op, the reveal effect never re-ran, and `prevMovesRef` stayed `null` into
play. The first real decrement (12→11) then hit the `prevMovesRef !== null`
guard, so the first reveal was **skipped**. That put every reveal one line
behind for the whole round (symptom 1), and at moves=0 the final line was never
marked revealed — so the end-of-round effect's `revealedChunkIndex < totalChunks
- 1` guard never released and the modal never opened (symptom 2, the freeze).
The bug was masked whenever the player changed the 2–4× drill count on the start
screen, because that genuinely changes the move count and re-runs the effect.

### Fix
Set `prevMovesRef.current = versesLevel.moves` (the move count at play start)
instead of `null`, at both touch points (Begin handler + restart path). The
first move is now correctly detected. The old `null` was defensive but
unnecessary — a move count going *up* (the 0→N mount bump) never triggers a
reveal, which only fires on a *decrease*. `npm run build` clean; no stale
references.

## Addendum — 2026-07-04 Session 7: use bonus moves in verses (tablet-verses v2.2)

Feature: bonus moves — earned and shown in the verses header, but previously
unspendable inside a verses game — can now be used. Tablet-first pilot per
user direction; phone-verses + sandbox ports pending. Reuses the existing
arcade bonus-move machinery (drop-down banner, in-header "End and carry"
button, below-target confirm) wired into the verses end-of-round flow.

### Scoping (decisions locked with user 2026-07-04)
1. **When offered.** Loss (0 moves, below target): the arcade banner drops down
   over the still-visible board instead of jumping to the passage screen —
   "Use bonus moves" resumes play; "End and carry" ends then shows the passage
   screen. Win (0 moves, at/above target): passage screen appears with an added
   "Use bonus moves" button that returns to the board.
2/3. **What they do / completion.** Extra swaps toward the target (passage stays
   fully revealed — the reveal is tied to regular moves, which stay at 0).
   Reaching target on bonus moves completes the level (stars + next-level
   unlock).
4. **Victory round.** A victory round already active on a WIN is kept (leftover
   novas pop at 1.5×). On a LOSS, crossing target during bonus moves completes
   the level but does NOT switch the 1.5× on — it wasn't a victory earned in
   regular play.

### Touch points (tablet-verses v2.1 → v2.2, all in the platform file)
- **Verses end-of-round effect:** added the banner-vs-passage decision (loss →
  banner; still-playing-bonus → wait; win/no-wallet/exhausted → passage screen,
  resetting the using-bonus flag on the way out).
- **3 input-freeze guards:** unfreeze the board during active bonus play
  (moves===0 but wallet remaining).
- **`endLevelCarryBonus`:** added a VERSES branch that opens the passage screen
  (verses' end-of-round) instead of the arcade win/lose gameState it replaces,
  recording completion when target was reached.
- **`resumeBonusFromPassage`:** new handler for the win-path button — closes the
  passage screen, returns to play, leaves the victory round on.
- **Passage-screen button matrix:** added the win-path "Use bonus moves" button
  (only when `won && bonusMoves > 0`).
- **Target→victory-round effect:** loss-path guard — suppress both the 1.5×
  activation AND the "✓ Target reached — 1.5×!" toast when the target is
  crossed during bonus play (the toast text hard-codes "1.5×", so leaving it
  advertised a boost that wasn't applied).

### Review refinement (this session)
- Playtest caught the "1.5×" toast still firing on the loss path when the target
  was hit on a bonus move (the victory-round *scoring* was correctly suppressed,
  but the toast text wasn't). Suppressed the toast on loss-path bonus play too;
  the gold ✓ in the header remains the target-reached signal.
