## Addendum — 2026-04-29 N-3 phone-418-verses v1.1 overflow fix shipped

First session of 2026-04-29; followed N-2's same-day ship of phone-418-verses v1.0 + phone-418 v13.2 on 2026-04-28 (committed 09acb59). User device-tested v1.0 on real iPhone hardware and reported two display bugs. N-3 is the responsive fix; mid-session reactive scope (not pre-scoped at session-start). Today is the first day of a new PROGRESS doc — 04-28 archived to `docs/archive/`.

**User-reported bugs:**

1. **Chrome overflow.** Header bar, rolling 3-chunk text bar, and bottom-instructions card all extended past the screen edge on the user's iPhone. Root cause: v1.0 inherited tablet-verses's chrome-sizing pattern of `width: ${boardWidth + 30}px` (= 448px on phone), plus a 20px page-wrapper padding. Total horizontal budget 488px overshot iPhone viewports (most are 390–430px).

2. **Bonus-moves text crowded + overflowed.** When the player earned bonus moves, the header score row (Score / Moves / Bonus moves: N / Target — and a 5th "End and carry moves forward" button when `usingBankedMoves`) had 4-to-5 items at 16px font totalling ~470–585px content on ~378px usable inner-header width. `justifyContent: 'space-around'` collapsed to zero spacing, then trailing items spilled past the right edge.

3. **(Parked.)** Tablet "End and carry moves forward" → are-you-sure popup not firing recently. User asked to defer; logged in DEFERRED.md "Known bugs." Investigation pending.

**Solution discussion (multi-message scoping pass):**

Item 1 — three options surfaced (A: trim chrome to board width + drop page padding; B: trim + shrink board tile size to 36px to fit narrower phones; C: responsive widths via percentages). User confirmed "the board barely fits" → phone is ≥418px → Solution A is enough (B unnecessary; C adds complexity that doesn't help on a phone where the board already fits).

Item 2 — three options surfaced (Solution A: bonus moves drops to its own row; B: smaller font when bonus active; C: flex-wrap). User confirmed A. Then on the related "End and carry moves forward" button crowding (which Solution A alone didn't fix — button still made row 1 too wide), four more options (I: button on its own row; II: shorten button text; III: move button outside header; IV: combine I + II). User noticed I was wasteful (3 rows for 2 indicators) and asked for a more elegant approach. **Option V: pair bonus-related items on row 2 — count left-aligned, button right-aligned via `marginLeft:'auto'`** — landed as the final design.

**What changed in v1.1 vs v1.0** (file [platforms/phone-418-verses/match3-v1.1-phone-418-verses.jsx](platforms/phone-418-verses/match3-v1.1-phone-418-verses.jsx); v1.0 archived to [platforms/phone-418-verses/archive/match3-v1.0-phone-418-verses.jsx](platforms/phone-418-verses/archive/match3-v1.0-phone-418-verses.jsx)):

*Chrome widths (Issue 1):*
- Outer page wrapper `padding: '20px'` + `paddingBottom: '60px'` collapsed to `padding: '0 0 60px 0'`. Recovers 40px of horizontal space.
- Header width `${boardWidth + 30}px` → `${boardWidth}px`.
- Rolling 3-chunk text bar width `${boardWidth + 30}px` → `${boardWidth}px`.
- Bottom instructions maxWidth `${boardWidth + 30}px` → `${boardWidth}px`.

*Score row restructure (Issue 2):*
- Single row split into a vertical column of two rows (`flexDirection: 'column'`, `gap: '6px'`).
- Row 1 (always): Score / Moves / Target — 3 items, stable layout, fits comfortably (~270px content on 378px usable).
- Row 2 (renders only when `bankedMoves > 0` OR `usingBankedMoves`): "Bonus moves: N" left-aligned + End-button right-aligned (button has `marginLeft: 'auto'` to anchor right whether or not the count precedes it).

*No canvas / board changes.* `TILE_SIZE` / `TILE_GAP` / ROWS / COLS untouched. Board still 418px (10 × 40 + 9 × 2). On viewports narrower than 418px, the board itself still overflows — out of scope (would require canvas responsive-scaling).

**Build verification.** `npm run build` clean, 66 modules transformed, zero warnings. Bundle: `phone418Verses-*.js` 77.99 kB / 23.49 kB gzipped (was 77.83 / 23.45 in v1.0; +0.16 kB from new comment text + the row 2 wrapper).

**Inherited TypeScript "hint" diagnostics** still present (the 9 unused-var hints inherited from v1.7 → v1.8 → v1.0). Out of scope for N-3.

**Dev server access from iPhone.** User asked how to test on iPhone. Vite dev server defaults to localhost-only — won't be reachable from a phone on the same Wi-Fi without `--host` flag. Two options to fix:
- **Run-time:** `npm run dev -- --host`. Vite then prints a Network URL like `http://192.168.1.x:5173/` to open in mobile Safari.

Not patched in N-3 (out of scope for the overflow fix); flag for next session if the user wants the persistent config change.

## Addendum — 2026-04-29 N-4 tablet v11.13 are-you-sure confirm extension shipped

Investigation triggered by user's 2026-04-29 report (originally parked during N-3 doc-update, reopened after N-3 commit pushed). User expected a confirm modal when clicking "End and carry moves forward" on the tablet bonus-moves prompt; reported it wasn't firing.

**Investigation finding (no regression):** the tablet v11.12 had **two** "End and carry moves forward" buttons with different confirm behavior, and v11.9's design intentionally only wired the confirm to one of them.

- **Bonus-moves prompt button** (visible at moves=0; the prompt the user was hitting): called `endLevelCarryBanked` directly. Per v11.9 file comment: "the bonus-moves prompt's End button is unchanged because that's a save after an already-failed turn."
- **In-header button** (visible only during active bonus-moves use, after "Use bonus moves" was clicked on the prompt): routed through `requestEndLevelCarryBanked` wrapper, which fires the confirm if below target.

User confirmed the prompt button is what they meant, and asked to extend the v11.9 design — the carry-forward decision *is* worth confirming, since bonus moves earned this round roll into the next round's pool and ending below target trades a chance at this round's win for that next-round resource.

**What shipped (Session N-4):**

*Tablet v11.12 → v11.13:*
- Archived `match3-v11.12-tablet.jsx` to `platforms/tablet/archive/`.
- Created `match3-v11.13-tablet.jsx` with single code change at the prompt button: `onClick={endLevelCarryBanked}` → `onClick={requestEndLevelCarryBanked}`. The wrapper's existing `wouldWin` check produces the right behavior in both prompt variants:
  - **Below target** (out-of-moves variant): `wouldWin` = false → confirm fires.
  - **Already won** (`promptWonAlready` / target reached variant): `targetReached` = true → `wouldWin` = true → no confirm, just ends.
- Added v11.13 prologue at top of file documenting the design extension.
- Updated v11.9 wrapper comment block to reflect that the prompt button now also routes through it.
- `src/main.jsx` repointed to v11.13.
- `index.html` tablet card description updated.

**Build verification.** `npm run build` clean. Tablet bundle 65.26 kB / 20.02 kB gzipped — unchanged (1-line code change, comments don't affect bundle).

**Behavioral note for re-verification.** The promptWonAlready variant ("🎯 Target reached! Keep playing with N bonus moves?") should still end without confirm when its End button is clicked — that path's behavior is unchanged. The change only affects the out-of-moves variant ("⚠️ Out of moves! You have N bonus moves").

**Files unchanged:** all other platform files. The same prompt button exists on phone-418-verses v1.1 (currently calls `endLevelCarryBanked` directly, mirroring tablet's pre-v11.13 behavior) — out of scope for N-4 per the strict-scope rule, but flag as a likely follow-up if user wants the same expansion across platforms. Cross-platform consistency is a real concern here — would be worth a single sweep rather than per-platform reactive fixes.

## Addendum — 2026-04-29 N-5 cross-platform prompt-button fix + phone-418-verses padding bump shipped

User authorized two bundled items same-day after N-4 shipped:
1. Apply N-4's prompt-button confirm fix to the other 3 platforms that already have the wrapper-and-modal architecture.
2. Phone-418-verses padding adjustment (Option B from the recommendation thread) to give text and the ← / ☀️ buttons more breathing room from the screen edge.

**Audit (which platforms got the fix vs. which didn't):**

Three platforms have the same setup as tablet v11.12 had — confirm modal already wired up for the in-header End button, but the prompt End button was still calling the function directly:
- Campaign tablet (v1.26 → v1.27)
- Tablet-verses (v1.8 → v1.9)
- Phone-418-verses (v1.1 → v1.2)

For these, fix was the same one-line change as N-4: `onClick={endLevelCarryBanked}` → `onClick={requestEndLevelCarryBanked}` on the prompt button. Wrapper's `wouldWin` check handles both prompt variants correctly (confirms below target; ends directly if `targetReached`).

Three other platforms work differently and weren't in scope:
- **Desktop v12.1** uses a different function name (`endGameCarryBanked`) and has no `requestEndLevelCarryBanked` wrapper at all. No confirm modal on either button.
- **Phone-418 arcade v13.2** same as desktop — no wrapper, no modal.
- **Phone-341 v12.1** likely same architecture.

For these three, applying the confirm would require porting both the wrapper function and the modal markup from tablet — a bigger change. Already on the deferred list under "Desktop + Phone 341 bonus-moves update" (carried forward from 2026-03-23 handoff). Logged separately in DEFERRED.md "Cross-platform parity."

**Phone-418-verses padding bump (Option B):**

Issue: after N-3 trimmed the chrome cards to `${boardWidth}px` (418px), they sat flush at the screen edges on a 418px viewport. On user's phone, text and the absolute-positioned ← / ☀️ buttons felt right up against the phone's edge.

Solution discussion produced two viable options (with a misleading recommendation pitch from me that user pushed back on):
- **Option A** — pull cards inward (narrower than board, e.g., 402px wide). Cards float inside screen edge by 8px each side; board stays edge-to-edge.
- **Option B** — keep cards at board width; bump internal card padding from 20 to 28; move absolute-positioned buttons from 8 to 16 from corner. Card edges still align with board edges.

I initially recommended A and asserted it as "what most iPhone apps look like." User asked to verify, and I had to walk it back — that claim was overconfident generalization, not a sourced fact. On closer look, the math reveals A and B produce identical content-spacing (content sits 28px from screen edge, ← button 16px from screen edge — same in both). The only real difference is whether the card edges align with the board edges. **B is the more natural look** since alignment with the board reads as more deliberate. User chose B; recommendation revised mid-thread.

**What changed in v1.2 vs v1.1** (file [platforms/phone-418-verses/match3-v1.2-phone-418-verses.jsx](platforms/phone-418-verses/match3-v1.2-phone-418-verses.jsx); v1.1 archived to [platforms/phone-418-verses/archive/match3-v1.1-phone-418-verses.jsx](platforms/phone-418-verses/archive/match3-v1.1-phone-418-verses.jsx)):
