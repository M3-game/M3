## Starting brief — next session: E-1b (simulation batch-runner admin UI)

All decisions scoped 2026-04-23 in this conversation. Ready to implement; no
open scoping questions.

**Version target:** tablet-sim `v1.1 → v1.2`. Archive v1.1 into
`platforms/tablet-sim/archive/`. Update `src/entry-sim.jsx` import path.

**UI placement.** New admin card in the existing tablet-sim admin wrapper,
alongside the inherited Playback / scoring-history cards. Title **"🤖
Simulation Batch Runner"**. Results render inline in the same card.

**Card layout (top to bottom):**
- Bot dropdown: `Bot: [1-Ply Heuristic ▼]` (only 1-Ply Heuristic in E-1b; MC
  option + MC Parameters sub-section added in E-2a).
- Target score input: admin-tunable, persists to sessionStorage. Default
  TBD — check `_SIM`'s current generation range (likely ~4000–6000). Fixed
  across all games in a batch.
- Preset buttons: `[10] [50] [100] [200] [1000]` games.
- During a run: preset buttons disabled; running preset shows live progress
  text ("Running… 37 / 100"); a Cancel button appears.
- Results panel (below controls):
  - Aggregate stats block (always visible).
  - Vertical-bar score histogram.
  - Per-game detail table (collapsible).
  - `[Copy JSON]` button.

**Async strategy:** `setTimeout(0)` yield after each `runGame()` call.
Verified sufficient — 1-ply runs 1000 games in ~12s (user console test
2026-04-23). No Web Worker needed for 1-ply; preserved for MC in E-2a.

**Aggregate stats displayed:**
- *Outcomes:* win rate · loss rate · stuck rate (as % of N).
- *Score:* mean · median (p50) · p10 · p90 · min · max.
- *Moves:* avg moves-to-win (winners only) · avg moves used (losers).
- *Cascades:* avg maxCombo per game · best single-game maxCombo.
- *Specials:* avg specialsCreated per game.
- *Bonus moves:* % of games earning ≥1 bonus move · max single-game bonus
  moves.
- *Runtime:* total batch seconds · avg ms per game.

**Vertical-bar score histogram** (below aggregates):
- x-axis: score buckets, auto-sized (500 or 1000 pts based on observed
  range).
- y-axis: count of games per bucket.
- Color split: loss-side buckets one color, win-side another (split at
  target line).
- Target line: vertical dashed marker at the target-score x-position.
- Optional tick marks for median / p10 / p90 along the x-axis.

**Per-game detail table (collapsible):**
- Columns: outcome, finalScore, movesUsed, maxCombo, specialsCreated,
  bonusMovesEarned, runtimeMs.
- Default expanded for ≤100-game runs, collapsed for 200 / 1000.

**Clipboard JSON shape (Option C — aggregates + raw + metadata header):**
```json
{
  "timestamp": "2026-04-23T12:34:56Z",
  "bot": "heuristic-1-ply",
  "simVersion": "v1.2-tablet-sim",
  "n": 100,
  "target": 5000,
  "aggregates": { "winRate": 0.42, "meanScore": 4840, "p10": ..., ... },
  "games": [ { "outcome": "win", "finalScore": 5240, ... }, ... ]
}
```
`botParams` field reserved for E-2a (absent / unused for 1-ply).

**`_SIM.runGame` API shape — set here so E-2a doesn't retrofit:**
```js
_SIM.runGame({
  bot: 'heuristic-1-ply',   // E-2a adds 'monte-carlo'
  target: 5000,             // admin-set fixed target; bypasses _SIM's internal generator
  botParams: { ... }        // optional; ignored by 1-ply; consumed by MC
})
```
Returns the same per-game result shape regardless of bot (`outcome`,
`finalScore`, `movesUsed`, `maxCombo`, `specialsCreated`,
`bonusMovesEarned`, `runtimeMs`). `bot` and `botParams` are echoed back in
the result so the batch-runner includes them in JSON metadata.

**Scoping decisions locked (see 2026-04-23 conversation for rationale):**
1. Session shape: one session, tablet-sim v1.1 → v1.2.
2. UI placement: new card in existing tablet-sim admin wrapper.
3. Async strategy: `setTimeout(0)` yield per game.
4. Presets: `[10] [50] [100] [200] [1000]`.
5. Stats set: as listed above.
6. Target score: admin-adjustable, fixed across the batch.
7. Clipboard JSON: Option C — aggregates + raw + metadata.

## Starting brief — session after E-1b: E-2a (Monte Carlo bot + Web Worker pool)

Scoped 2026-04-23 alongside E-1b. All decisions locked; a few tuning
defaults are provisional and revisit in E-2b.

**Version target:** tablet-sim `v1.2 → v1.3`. Archive v1.2 into
`platforms/tablet-sim/archive/`. Update `src/entry-sim.jsx` import path.

**Scope summary:**
- Add a Monte Carlo bot implementation to the `_SIM` namespace, selectable
  via the bot dropdown in E-1b's batch runner.
- When "Monte Carlo" is selected, an **MC Parameters** sub-section expands
  below the dropdown:
  - **N** (playouts per candidate swap): default **30**, range 10–200.
    Tunable admin input.
  - **Depth-cap**: default **5**, range 3–20. Tunable admin input. (User
    specifically asked for tunability here to test whether lookahead past
    ~10 moves matters — intuition is it shouldn't, given match-3's state
    divergence after cascades and refills.)
  - **Rollout strategy**: 1-Ply Heuristic / Random. Default **1-Ply
    Heuristic** (less noisy per rollout; useful signal at lower N). Admin
    toggle so E-2b can compare the two.
  - **Workers** (pool size): default `navigator.hardwareConcurrency - 1`,
    range 1–hardwareConcurrency. Admin input.

**Performance architecture — Worker pool:**
- New file `platforms/tablet-sim/sim-worker.js` (or similar) hosts `_SIM`
  logic for the worker context.
- Each worker runs full games (one game per worker at a time). Main thread
  orchestrates: dispatches games, aggregates results, updates progress UI,
  handles Cancel.
- Pool lifecycle: spun up on Run, terminated on Cancel or batch completion.

**Runtime math validating the worker pool decision** (from user's 12s /
1000-game 1-ply batch on 2026-04-23):
- 1-ply ≈ 12ms/game → ~0.3ms per real move.
- At N=30, depth-cap 5, 1-ply-heuristic rollouts: ~1.2s per real MC move →
  ~50s per MC game.
- 100-game MC batch sync / single-worker: ~80 min. At 4 workers: ~20 min.
  At 8 workers: ~10 min.

**Clipboard JSON metadata additions:** `botParams: { n, depthCap,
rolloutStrategy, workers }` when `bot === 'monte-carlo'`. Absent for 1-ply.

**Stats schema — no new per-game metrics.** Existing fields (outcome,
finalScore, movesUsed, maxCombo, specialsCreated, bonusMovesEarned,
runtimeMs) apply equally to both bots. Distributions will differ; the
metrics themselves carry over. Results display shows bot name + key params
at the top (e.g., "Monte Carlo — N=30, depth 5, 1-ply rollouts — 100
games, 61% win rate…").

**Provisional defaults to revisit in E-2b:** N=30, depth-cap=5, 1-ply-
heuristic rollouts.

**Scoping decisions locked:**
1. Session shape: split into E-2a (implementation) + E-2b (tuning).
2. MC algorithm shape: 1-ply-heuristic rollouts default, tunable to random;
   N=30 default, range 10–200, tunable; depth-cap=5 default, range 3–20,
   tunable.
3. Performance strategy: Web Worker pool, default pool size
   `hardwareConcurrency - 1`, admin-tunable.
4. Architectural integration with E-1b: bot selector dropdown in E-1b's
   card; MC parameters sub-section; `_SIM.runGame({bot, target, botParams})`

## Addendum — 2026-04-23 scoping session: E-1b, E-2a, E-2b + E-1a2 fix

Long scoping conversation covering all three upcoming simulation sessions.
Key decisions captured in the starting briefs above. Highlights worth
persisting here:

- **"0 bonus moves in 50 games" was an artifact, not a signal.** The E-1a
  50-game console run showed zero games crossing 10k for a bonus move.
  User flagged mid-conversation that the bot had been told to stop at
  target score, so it never kept playing to accumulate past it. One-line
  fix (E-1a2) reversed the behavior. Rerunning with v1.1 will give real
  data; the "MC will cross 10k where 1-ply can't" motivation softens until
  we see fresh post-fix numbers.

- **Runtime math for MC.** User ran a 1000-game 1-ply batch in ~12s wall-
  clock. That gave us concrete per-move cost (~0.3ms) and realistic MC
  compute estimates: even at aggressive params MC is firmly Web-Worker +
  depth-cap territory. Sync execution off the table. Worker pool worth the
  ~75 lines of orchestration code for 4–8× speedup over single worker.

- **Target score — admin-adjustable not dynamic for sim.** User observed
  that `_SIM` in v1.0/v1.1 generates unrounded targets (e.g., 4837),
  whereas the live game rounds to 100. E-1b will pass an admin-set fixed
  target straight into `runGame`, bypassing `_SIM`'s internal generator
  for batch runs. A DEFERRED item added to tighten `_SIM`'s target
  generation to match live (round to 100) for any context where auto-
  generated targets are still used.

- **Depth-cap empirical range.** User wants depth-cap tunable specifically
  to test whether lookahead past ~10 moves matters — intuition is it
  shouldn't given match-3's state divergence after cascades and refills.
  E-2a defaults depth-cap=5 with tunable range 3–20 so E-2b can
  empirically check.

- **Framework designed to host both bots from E-1b onward.** `_SIM.runGame`
  API gets its final `{bot, target, botParams}` shape in E-1b (even though
  only one bot exists there) so E-2a doesn't retrofit. JSON metadata
  already includes a `bot` field. Stats schema stays unchanged across
  bots — distributions differ; metrics don't.
