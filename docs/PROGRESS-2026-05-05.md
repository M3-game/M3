**Bundled side-fix: tablet-rewardmode v1.3 → v1.4.** During Mechanic
B scoping, user observed that in rewardmode-sandbox the big-turn
popup sometimes "fires while cascades are still happening, and the
nova drops during the same turn." Investigation traced the timing:
`setTurnComplete(true)` only fires post-applyGravity at end-of-cascade
(line 3675), so logically the consumer cannot fire during turn N.
But the useEffect runs immediately on turnComplete flip, while
staggered tile-drop animations from the last refill are still
settling visually. Fix: defer the popup + roll by
`BIG_TURN_POPUP_DELAY_MS = 400` inside the useEffect, with cleanup
clearing the timer if turnComplete flips back to false (player swaps
before timer fires). Forfeiting telegraph on a fast swap is the
intentional tradeoff. The same pattern is what got ported into VS-1
from the start, so VS-1 inherits the corrected behavior.

**Refined hypothesis on the original "same-turn nova" perception
(user, post-implementation 2026-05-05).** With neighbor-bias active,
refilled tiles cluster by color, raising the rate of natural 5+/7+
matches landing in the refill. Hypernova requires 7+ connected
tiles (per `HYPERNOVA_MIN_TILES`), and a big turn (≥12 tiles
cleared) means lots of refill cells = lots of opportunities for
naturally-clustered new matches. So a hypernova appearing "same
turn as the popup" may not be the queued big-turn drop firing
early — it may be a regular special tile being CREATED NATURALLY
by the bias-induced cluster, completely independent of the big-
turn-drop mechanism. This is by design (Mechanic A + the existing
4+/5+/7+ special-creation rules interact to produce more specials
overall, especially on big turns). The v1.4 popup-delay fix is
still defensible as a general "popups should appear after animations
settle" hygiene improvement, but it neither caused nor cures the
natural-spawn interaction the user was observing. Captured here +
in a code comment in `phone-verses-sandbox` near the
`NEIGHBOR_BIAS_PCT` definition so a future investigation pass
doesn't re-derive it from scratch. If a future tuning pass wants
to visually distinguish "natural cluster spawn" from "big-turn
queued drop," the consumer in fillEmptySpaces already logs
`[VS-1 big_turn_drop]`; instrumenting natural special-creation in
processMatches with a paired `natural_special_create` log would
give a clean diff.
